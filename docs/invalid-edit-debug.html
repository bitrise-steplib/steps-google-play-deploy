Invalid Edit State — How it happens & how this branch helps debug it

Step: steps-google-play-deploy · Branch: debug-invalid-edit · Experimental trackless upload

The step talks to the Google Play Android Publisher API using a single transactional edit. You Insert an edit, mutate it (upload artifacts, assign tracks), then Commit it. The commit is the moment Google validates the whole transaction.

The experimental trackless feature makes track optional. When no track is provided, the step uploads the APK/AAB but skips the track update. That can leave the edit in a state Google rejects at commit time: Error 400 — The Edit is in an invalid state, and may not be committed

How we get into an invalid edit state

Root cause: an uploaded APK/AAB that is not referenced by any track release makes the edit incomplete. Google only surfaces this at Commit (or Validate in dry-run), with a generic message that doesn't name the offending version code.

What this branch logs to help debug it

All extra logging is gated behind verbose_log (IsDebugLog) so normal runs stay quiet. Three things were added to executeEdit:

1. Current edit details verbose

logEditDetails() calls editsService.Get right after insert and logs the live edit:

Current edit:
- editID: 04faa1c2-...-9b3e
- expiryTimeSeconds: 1735689600

Confirms the edit exists and is still within its validity window (edits expire). Note: the Play API has no endpoint to list open edits — only the active edit can be inspected.

2. Available tracks verbose

listTracks() logs the tracks visible on the edit, so you can see what assignment targets exist.

3. Uploaded artifacts without a track the key signal

listUntrackedArtifacts() cross-references uploaded artifacts against track assignments:

  • trackedVersionCodes() — gathers every version code referenced by any track release (Tracks.List → releases → versionCodes).
  • Apks.List + Bundles.List — every artifact present in the edit.
  • The diff (uploaded ∖ tracked) is logged — these are exactly the artifacts that will fail the commit:
Uploaded artifacts without a track:
- APK version code (no track): 4120
- AAB version code (no track): 4121

Result: instead of a bare "invalid state" failure, the log now pinpoints which uploaded version codes are orphaned (no track). In trackless mode that's expected and explains the rejection; in a normal run a non-empty list reveals an artifact that updateTracks failed to cover.
